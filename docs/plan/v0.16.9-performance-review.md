# v0.16.9 performance and persistence review

Status: Investigation completed; remediation pending.

On 2026-10-07, the external `/tmp/report.txt` analysis was checked against local
HEAD `e8f1429` and the downloaded `0.16.9` Linux binaries in isolated Docker
containers. No product code or existing test nodes were changed. This was not
an exact-commit public release verification or a rerun of the full functional
suite.

The full local report, benchmark scripts, configurations, measurements and
original damaged store are retained at
`/tmp/operon-review-yAFunp/review.md`. These temporary artifacts are local
evidence and are not shipped with the repository.

## Findings

- Default store persistence increased repeated open/write/close 4KiB file
  operations from approximately 1.3–1.4ms without a store to 4.5–5.1ms.
  Keeping store appends but bypassing `fdatasync` through a benchmark-only
  preload library measured 1.4–1.5ms. This supports synchronous persistence
  as a major contributor; it is not a recommended deployment configuration.
- Concurrent audit appends produced concatenated JSON records on one line.
  Restarting the isolated daemon failed with `state-restore`, reporting
  trailing characters at column 234. A shared serialized writer boundary is
  required before increasing write concurrency or batching persistence.
- A failed `WriteFile` stream replaced an original test file's contents with
  the accepted partial chunk. The error did not restore the original file.
- `WriteFileRange` rejected 4MiB and 8MiB data fields at the default 4MiB
  encoded-message receive limit. Application chunk limits and transport
  limits need alignment with protobuf overhead accounted for.
- `ReadFileRange` requests for 4MiB and 8MiB returned only 2MiB on a 256MiB
  file. The handler uses one read and Tokio's default file buffer limit is
  2MiB. This violates the documented requested-range behavior when data
  remains before EOF; fix the fill loop together with transport limits.
- Kernel attribute caching already works: 100 consecutive stat calls
  generated one remote Stat RPC, and another 100 calls after 1.1 seconds
  generated one more. The report's claim of no attribute cache is incorrect.
- Four readers of the same 256MiB file consumed about one file's worth of
  network bytes, despite reading 1GiB in aggregate. Four distinct files
  transferred about 1GiB and measured approximately 412MiB/s. Same-file
  aggregate throughput does not prove remote linear scaling.

## Follow-up scope

Prioritize store record integrity and restart recovery, then failed-write
semantics and range/message contracts. Evaluate serialized group commit with
explicit durability, error, backpressure and shutdown behavior. Reduce
write-side Stat calls using authoritative metadata, reuse CLI connections
across pages, and tune read-stream chunks with repeatable measurements.

High-BDP transport behavior, disconnect deadlines, exec-log throughput and
large-directory pagination remain unmeasured. No fixed post-optimization
latency or throughput target has been established.

The planned implementation phases and acceptance criteria are recorded in
`docs/plan/v0.18.13-runtime-correctness-performance-roadmap.md` and
development-phases.md (Phases 126–130). Implementation has not started.
