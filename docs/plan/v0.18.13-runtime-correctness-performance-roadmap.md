# Runtime correctness and performance roadmap

Status: Completed. Full Linux and native macOS/Windows acceptance plus
exact-commit pre-tag gates passed; publication is tracked in Phase 131.

This roadmap follows Phase 125's v0.16.9 investigation. The `v0.18.13` through
`v0.18.17` names below are internal maintenance batch identifiers, not public
artifact versions. Public version changes and publication are decided after

## Phase 126: v0.18.13 Store record integrity and restart recovery

Status: Completed, including native platform validation.

Problem: concurrent appends can concatenate JSON records on one line. The
daemon then cannot restore state on restart. Moving the same writes to more
blocking threads without serialization would retain the race.

Scope:

- Give all clones of a StoreWriter one shared append boundary for exec
  records, exec logs and audit events. Serialize each complete JSONL record,
  including its newline, and coordinate concurrent appends to the same store.
- Preserve the default synchronous `Always` policy in this phase; keep this
  correctness fix separate from batching and delayed persistence.
- Preserve private-file creation, regular-file validation and no-follow
  protections. Do not weaken workspace/config containment checks.
- Define recovery for previously generated concatenated records and a final
  incomplete record. Preserve the original file, recover only unambiguous
  complete JSON objects with their order intact, and surface explicit
  diagnostics. Never silently discard malformed interior data or invent
  missing events. Tail recovery must be distinguished from interior corruption.
- Consolidate loader behavior so exec, log and audit restoration agree on
  recovered records. Avoid changing retention or adding compaction here.
- Keep persistence errors observable. Document that current audit persistence
  failures are logged rather than automatically making an RPC fail; do not
  claim a stronger audit durability contract than the implementation provides.

Acceptance:

- Concurrent mixed-record appends through cloned writers preserve record
  count, unique identifiers, per-producer order and independently parseable
  JSONL lines. Test with default sync enabled as well as disabled.
- A real daemon restart after concurrent workload restores exec, log and
  audit visibility and does not fail with the reproduced trailing-characters
  error.
- Fixtures cover concatenated complete records, an incomplete tail, malformed
  interior data, Unicode and escaped braces. Recovery preserves the source
  and explains any unavailable tail data; unsupported corruption fails clearly.
- Existing symlink/private-file tests and writer failure tests remain valid.

Primary modules: `operon-store`, daemon audit/exec persistence and startup state
restoration. Run focused store/daemon tests and the existing restart validation.

## Phase 127: v0.18.14 Range-read contract and gRPC message limits

Status: Completed through real Rust/SDK gRPC clients and native CI.

Problem: a single Tokio read can return 2MiB for a valid 8MiB request with more
data available. Application data limits also exceed default transport receive
limits. This is a correctness fix, not just a throughput optimization.

Scope:

- Read until the requested size is filled, actual EOF is reached, or an I/O
  error occurs. Short reads before EOF must not prematurely finish the RPC.
  Return empty data for size zero or an offset at/beyond EOF. Do not use
  `read_exact` in a way that turns an ordinary EOF into an RPC error.
- Preserve offset overflow, maximum object size, authorization, containment
  and one logical audit event per RPC.
- Centralize the 8MiB filesystem data limit and an explicit bounded encoded
  message limit, initially 16MiB, leaving room for protobuf metadata. Keep the
  application data checks: larger transport limits do not allow larger data.
- Apply compatible send/receive limits to the daemon generated service,
  shared Rust clients, mount clients constructed from channels, and the
  TypeScript SDK transport. Configure the generated service/client rather
  than assuming Server::builder or a Channel sets codec limits.
- Specify live-read semantics: no snapshot guarantee during concurrent file
  modification; fewer bytes are legitimate after actual EOF is observed.
- Update PROTOCOL.md and runtime API docs with range, EOF and limit behavior;
  regenerate SDK/protocol assets only if their schema actually changes.

Acceptance:

- Exact content and length for nonzero-offset reads around 2MiB and 4MiB,
  and an 8MiB read from a larger file, through real gRPC.
- Zero-size, exact-EOF, beyond-EOF and range-crossing-EOF cases; range overflow
  and oversize rejection; small injected reads to verify the fill loop.
- Exactly 8MiB range writes and full 8MiB responses work through Rust and SDK
  clients; application limit + 1 is rejected. Over-limit encoded messages
  remain bounded and fail predictably.
- Mount/read helpers and SDK public API checks remain compatible. Validate
  actual byte contents, not just successful status or byte count.

Primary modules: daemon fs service, protocol transport constants,
`operon-grpc-client`, mount remote client and SDK client transport. Run focused
Rust tests plus SDK typecheck/test/build and real-daemon boundary cases.

## Phase 128: v0.18.15 Streaming file replacement failure semantics

Status: Completed, including native replacement/ACL/sharing acceptance.

Problem: WriteFile truncates the target before the stream is complete. A
rejected or interrupted stream leaves partial content in an existing file.

Scope:

- Stage full-file replacements in a uniquely created temporary file in the
  destination directory. Publish only after valid stream completion and an
  explicitly awaited flush. Remove abandoned staging files on handled errors
  or cancellation; define cleanup for leftovers after a process crash.
- Commit through platform-appropriate atomic replacement where supported.
  Document the file-data/directory durability guarantee separately from
  store fsync; do not equate a flushed userspace buffer with power-loss safety.
- Recheck mutation preconditions at commit. Define coordination with range
  writes, truncate, rename, copy and other replacements; avoid a stale
  precondition passing only because it was checked before stream reception.
- Preserve containment and leaf-symlink behavior. Define permission/ACL
  preservation, destination absence and Windows open-file replacement errors.
- Document the intentional inode/handle change for whole-file replacement:
  existing open handles may continue referencing the old object. Hard-link
  behavior must be stated and tested. Atomic replacement must not silently
  be described as behavior-preserving in-place truncation.
- Keep WriteFileRange as write-through in-place mutation. Do not introduce
  mount write-back caching or promise multi-writer transactional isolation.

Acceptance:

- An existing file remains byte-identical after malformed chunks, oversize,
  transport cancellation and injected write/flush/commit errors; an absent
  target remains absent until successful commit.
- Successful empty and nonempty replacement, final version, permissions,
  symlink handling and supported-platform behavior are checked.
- A concurrent change invalidates expected_version/require_absent at commit
  under the documented coordination boundary.
- Verify visibility through open handles/hard links and cleanup of temporary
  files. Audit outcome must agree with commit success or failure.

Primary modules: daemon fs service and platform filesystem helpers. Run real
stream-failure cases on Linux and platform smoke checks on macOS/Windows.

## Phase 129: v0.18.16 Serialized store I/O and group commit

Status: Completed; default Always remains unchanged.

Goal: reduce synchronous persistence overhead while keeping an explicit
durability and failure contract.

Scope:

- Move blocking store work from Tokio workers behind one writer with a
  bounded queue. Reuse its file handle and directory setup while preserving
  safe opening, ordering and writer failure visibility.
- Implement group commit for concurrent requests. Under default Always,
  acknowledge an append only after the group containing it has synced.
  Grouping must not add an artificial fixed delay to every sequential RPC.
- Preserve exec/audit ordering and terminal-record visibility. Retain complete
  exec logs; head/tail truncation is outside this optimization.
- If periodic syncing is added, expose it as an explicit opt-in with bounded
  flush interval and documented possible loss after a crash. Distinguish
  append acceptance, disk write and durable completion; queued data alone
  does not count as durable.
- Define queue backpressure, write/sync failure propagation, orderly shutdown
  drain and timeout behavior. Add config explain/doctor/docs coverage if a
  new user-facing persistence setting is introduced.

Acceptance:

- Mixed concurrent records remain valid and restore correctly; Always does
  not acknowledge before sync, verified through an instrumented writer.
- Queue saturation, writer failure, shutdown and opt-in periodic behavior are
  tested. No unbounded queue and no blocking disk work on Tokio workers.
- Benchmark Always and any periodic mode separately. Compare sequential and
  concurrent small-file loads and high-output exec, including record counts,
  sync counts, CPU, memory, mean/p50/p95/p99 and restart outcomes.
- Record measured gains and tradeoffs; do not promise 1–2ms under Always.

## Phase 130: v0.18.17 Filesystem RPC efficiency and reproducible benchmarks

Status: Completed with repeated exact-commit Docker ops/s measurements.

Scope:

- Add optional authoritative post-mutation metadata to filesystem write
  responses, using additive protocol fields and regenerated bindings. Keep
  old fields compatible; older peers lacking metadata use the existing Stat
  fallback. Define mixed-version compatibility before removing any RPC.
- Use returned metadata for mount write/create inode refresh to remove
  redundant Stat calls. Do not guess size/mtime locally or extend the current
  one-second kernel attribute cache without a separately justified contract.
- Reuse a connected client for CLI filesystem and capability pagination.
- Increase streaming read chunks, starting with 64KiB and measuring other
  sizes. Avoid changing generated byte types/public SDK contracts solely to
  remove a to_vec unless measurements justify that additional scope.
- Add a reproducible Docker benchmark harness using isolated data and real
  binaries. Separate persistent-file writes, create/write/close, process-start
  overhead, kernel cache behavior and same-file/different-file concurrency.
- Collect client/server network bytes, RPC counts, exact data integrity and
  latency distributions. Label client-remount cold reads separately from
  server disk-cache cold reads; avoid global host cache drops.

Acceptance:

- Mutation metadata agrees with daemon Stat after write, sparse extension,
  truncate and create; older-response fallback remains functional.
- RPC counts fall for the targeted write/create paths without changing
  write-through, errno, version or cache freshness semantics.
- Multi-page CLI operations reuse a connection and preserve pagination
  output/error behavior. Larger read chunks preserve binary data and errors.
- Repeat benchmark runs against a recorded baseline commit and candidate
  commit on the same environment. Keep correctness checks mandatory; large
  host-sensitive benchmarks are opt-in rather than flaky CI speed gates.
- Run SDK public API/typecheck/test/build, workspace tests, core validations
  and docs/help/skills synchronization for the surfaces actually changed.

## Implementation and validation evidence (2026-10-07)

Local implementation covers all five phases. Default store durability remains
Always; no periodic policy, log truncation, extended attribute-cache TTL or
mount write-back was introduced. Store writes run on a dedicated OS thread;
the synchronous caller API still waits for acknowledgement. The daemon uses
`block_in_place` on multithread Tokio runtimes while waiting. Queue capacity is
256 records, batch capacity is 64, and grouping introduces no fixed timer delay.
Last-producer disconnect drains the queue and joins the writer; no bounded
shutdown timeout is promised if the OS stalls in disk I/O.

Validation:

- `cargo test --workspace --locked`: passed on Linux. The added cancellation
  and empty-replacement test also passed in the focused rerun.
- `bash scripts/verify-runtime-correctness-performance.sh`: passed; 13 store
  tests, filesystem-service failure/ACL tests, real TCP gRPC limits/bytes tests,
  31 mount tests, CLI pagination connection-count tests, SDK typecheck and 16
  SDK tests. Registered in the runtime CI group.
- SDK public API contract and build: passed. Existing real-daemon integration,
  store-backed audit visibility and runtime-hardening scripts: passed.
- All validation groups passed: core 49, runtime 15, SDK 13, Linux system 4.
- `cargo check -p operond --tests --target x86_64-pc-windows-gnu --locked` and
  the equivalent `x86_64-apple-darwin` check: passed. These are compile checks,
  not evidence of native ACL, replacement, linking or filesystem behavior.
- Native macOS/Windows store, filesystem-service, real gRPC and pagination
  tests passed in final CI `37635047230`. Direct Win32 ACL tests avoid runner
  PowerShell module assumptions while testing real DACL/sharing semantics.
- On `f395ae5af18a1c2a62219b1974a99e5b11498f81`, CodeQL `37635047043`,
  cross-platform live mount `37635047604` and Windows runner `37635052512` passed.

### Primary ops/s comparison for v0.16.10

The final two-round benchmark is `/tmp/operon-phases-zpjxhhzb`, using binaries
built from clean release commit `f395ae5af18a1c2a62219b1974a99e5b11498f81`.
Completed ops/s is the primary comparison. One
small-file operation is a complete workload iteration; one transfer operation
is one complete 64MiB file. Failed CLI operations count as zero, not successful
throughput. Different workload units must not be compared directly.

| Completed operations/second | Baseline rounds 0 / 1 | Candidate rounds 0 / 1 |
| --- | --- | --- |
| Persistent 4KiB write | 560 / 561 | 884 / 881 |
| Create/write/close 4KiB file | 223 / 212 | 323 / 310 |
| Create empty file | 365 / 359 | 537 / 495 |
| CLI streaming 64MiB file read | 1.69 / 1.62 | 9.12 / 8.26 |
| Four distinct concurrent 64MiB FUSE reads | 6.49 / 6.56 | 5.83 / 5.59 |
| CLI exec with 4MiB output | 0 / 0 (decode failure) | 2.93 / 2.77 |

Persistent writes improve 57–58%, create/write/close improves 45–46%, and CLI
streaming reads improve 5.1–5.4x in these matched rounds. Distinct-file parallel
FUSE read ops/s decreases 10–15%; this is a disclosed tradeoff, not a read
speedup claim. Absolute values remain host-dependent supporting evidence.
Candidate has zero invalid store lines and passes both real restarts; baseline
has 29/44 invalid lines and both restarts fail. Real workload sync counts are
11833/11899 versus 7855/7831, without bypassing sync. Binary hashes and detailed
latency, byte and resource measurements are retained in the evidence directory.

### Earlier absolute-value measurements (reference only)

Earlier release-mode Linux binary evidence is retained at
`/tmp/operon-phases-nfchzsgq`. The harness records SHA256 for each binary, source
HEAD/dirty status, exact bytes, network counters, audit deltas, resource counters,
sync timings and restart results. Baseline binaries are from the inspected
`e8f1429` / v0.16.9 tree; candidate binaries are the uncommitted implementation,
not an invented candidate commit. Run order was baseline/candidate then
candidate/baseline. Each run used 500 operations and 64MiB file workloads.

| Measurement | Baseline (two runs) | Candidate (two runs) |
| --- | --- | --- |
| Invalid JSONL lines | 25 / 35 | 0 / 0 |
| Real restart + restored exec/log/audit | failed / failed | passed / passed |
| Persistent 4KiB writes, mean | 1.79 / 1.96ms | 1.19 / 1.06ms |
| Persistent writes, p95 | 2.19 / 2.61ms | 1.53 / 1.33ms |
| Persistent writes, p99 | 2.61 / 3.02ms | 1.70 / 1.64ms |
| Workload fdatasync calls | 11864 / 11844 | 7824 / 7821 |
| Sum of fdatasync elapsed time | 6.41 / 6.29s | 4.12 / 3.79s |
| CLI streaming read, 64MiB | 0.598 / 0.579s | 0.116 / 0.111s |
| FUSE client-remount read, 64MiB | 0.304 / 0.312s | 0.334 / 0.286s |

Persistent-write Stat audit count fell from 503 to 2 for 500 writes. Group
commit and eliminated RPCs together reduced sync count about 34%; this is not
an isolated measurement of group commit. Instrumentation observes real sync
calls and does not disable them. CLI streaming read improved about 5x, but
ordinary FUSE reads have no general speedup; the distinct-file parallel case
was 8–17% slower and remains a measured tradeoff to investigate. Candidate
4MiB exec output passed CLI transport and persisted all bytes (plus the 14-byte
restart marker); baseline CLI decoding failed at the old 4MiB message limit.
Resource measurements include cgroup page cache and candidate SDK preflight,
so they are not a matched isolated-RSS comparison or a memory-improvement claim.

## Deferred work and release boundaries

Transport deadlines/keepalive and high-BDP window tuning need their own
fault-injection and realistic RTT measurements. Streaming exec sessions,
service tunnels and long transfers must not inherit a blanket short timeout.
They remain follow-up work rather than a claimed benefit of this roadmap.

Directory snapshots/cursors, mount directory caches, store compaction,
workspace path/fd caches and changing mount runtime topology are also
deferred. Their consistency, security or lifecycle contracts need separate
evidence and scope.

Each completed phase updates development-phases.md and replaces planned
acceptance with actual command/results evidence. Cross-platform CI is
required for filesystem/store changes. Public publication requires a
separate exact-commit gate and artifact verification; passing these phases
alone does not publish a release.
